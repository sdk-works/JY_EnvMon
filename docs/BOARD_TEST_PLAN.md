# JY_EnvMon 上板测试计划（确认字保守策略版）

> 适用固件：仓库 HEAD（在 `3fa0bdd` 基础上改了确认字策略）
> 文本记为 `HEAD`；下文所有数字都按 `DTU_FAST_TEST_RHYTHM` 打开（10s/条、2s 槽）计算。

## 0. 本轮相对 3fa0bdd 改了什么（上板前必须知道）

| 项 | 3fa0bdd | 本轮 |
|---|---|---|
| 确认字非 FF 非 00 | 当成"已确认"→ 出队，**不再补传** | 当成"状态不确定"→ **保留补传资格** |
| 不确定状态如何解开 | 无（直接出队） | 复制到新槽（确认字为擦除态）→ 在新槽写确认字 → 出队 |
| 重启扫描 | 不确定值不算待发 | 不确定值**算待发**；同一 `(boot_id,seq)` 有多份时以靠后的槽为准（去重陈旧副本） |
| 记录格式 | — | **未变**，见 §5 |

理由：云端按 `msg_id` 幂等去重，重复上传可处理；误判成功造成漏传不可补救。
所以宁可多传一次，也不能少传一条。

## 1. 烧录（关键：不要全片擦除）

**必须保留 S4~S7**，否则身份和缓存一起没了：

| 扇区 | 地址范围 | 内容 |
|---|---|---|
| S4 | 0x08010000–0x0801FFFF (64KB) | 元数据 A（boot_id/代次） |
| S5 | 0x08020000–0x0803FFFF (128KB) | 数据缓存 A（待发记录） |
| S6 | 0x08040000–0x0805FFFF (128KB) | 数据缓存 B |
| S7 | 0x08060000–0x0807FFFF (128KB) | 元数据 B |

代码区只有 0x08000000–0x0800FFFF（22.08KB），`.hex` 里只含这一段。

Keil 里烧：
1. `Options for Target` → `Debug` → `Settings` → `Flash Download`
2. **取消勾选 `Erase Full Chip`，改选 `Erase Sectors`**
3. 勾 `Program` + `Verify`，下载

用 ST-LINK Utility / STM32CubeProgrammer 时，擦除范围填 `0x08000000`–`0x0800FFFF`，
**不要**点 `Full chip erase`。

> 全片擦除的后果：boot_id 归零 → 下次开机从 1 重新编号 → 与云端历史 `msg_id` 撞号；
> 同时 2044 条未上传缓存全部丢失。这两件事都不会报警，只会表现为"云端数据乱序/缺失"。

烧完先确认一件事：**重启后云端看到的 `boot_id` 应该比上次大 1，不是回到 1**。
如果回到 1，说明 S4/S7 被擦了，立刻停测。

## 2. 观测手段（设备本身不显示队列状态）

设备上没有 pending/dropped 的显示，所以用两条非侵入通道：

1. **云端**（主）：`msg_id` = `JY001/<boot_id>/<seq>`，看序列连续性、到达节奏、重复 `msg_id` 去重命中次数。
2. **串口抓包**（辅，可选）：USB-TTL 只接 RX 并联在 USART1 上（只收不发），
   可抓到每一帧 JSON 和每一帧 ACK，不影响通信。用于定位"发了没收到 ACK"还是"根本没发"。

## 3. 时间/容量换算（10s 节律）

| 量 | 数值 |
|---|---|
| 单扇区容量 | 2044 条 |
| 填满一个扇区 | 2044 × 10s = **5h40m40s** |
| 满后每批淘汰 | 255 条（容量 1/8） |
| 每批之间的间隔 | 255 × 10s = **42m30s** |
| 满缓存后每小时迁移次数 | ≈ 1.41 次（每次 2 个扇区擦除） |
| 2044 条补传清空（2s 槽，3 历史插 1 最新） | ≈ **68 分钟** |

第 2045 条追加成功后，队列 = 2044 − 255 + 1 = **1790 条**
（1789 是"丢弃后、追加前"的中间态，不是稳态）。

迁移的阻塞时间分两种，别混：
- **正常联网**：迁移时 pending 只有 0~几条，复制量极小，耗时毫秒级，看不出来。
- **断网积压**：迁移要复制 1789~2044 条（约 130KB），阻塞主循环约 1~2 秒。
  此时 485 采集可能漏 1~2 轮（无看门狗，不会复位），属预期。

## 4. 四组上板测试

### A. 正常联网、ACK 正常

- **前置**：云端在线并正常回 `status=stored`；从空缓存开始（或记下起始 seq）。
- **操作**：连续跑 **≥ 2 个扇区**，即 4088 条 ≈ **11h20m**。中途重启 1 次。
- **预期**：
  - 云端 `seq` 连续无缺口，`msg_id` 无重复（或重复极少且被去重）；
  - 每 2044 条（≈5h40m）发生一次迁移，迁移瞬间最多晚 1~2 帧，**不丢**；
  - `dropped` 不增加（表现：`seq` 从头到尾连续）；
  - 重启后 `boot_id` +1，`seq` 从 1 重新开始，积压为 0 或仅当前在途 1 条。
- **判定失败的含义**：`seq` 有缺口 = 丢数据；`boot_id` 回退 = 身份存储被破坏；
  迁移瞬间长于 10s 的空白 = 迁移路径有阻塞问题。

### B. 断网积压（不给 ACK）

- **前置**：A 完成后，断开上行（拔 DTU 或云端禁用该设备）。
- **操作**：保持采样 **≥ 6 小时**（跨过 2044 条），观察是否按 42m30s 的节奏继续淘汰。
- **预期**：
  - 前 5h40m：队列线性增长到 2044；
  - 第 2045 条：淘汰最旧 255 条 + 迁移（此时队列 1790）；
  - 之后每 42m30s 再来一次（每批 255 条）；
  - 全程无复位、无死机、屏幕显示正常。
- **判定**：恢复后云端最早收到的 `seq` 应等于「最后一次淘汰的边界」，
  缺口长度 = 255 × 批次数。**这是设计允许的丢弃，不是 bug**，
  但缺口必须严格是 255 的整数倍 —— 不是整数倍说明丢在了别处。
- 注：`dropped` 计数不上报云端，只能靠 `seq` 缺口反推。

### C. 恢复补传

- **前置**：B 结束、仍处于断网积压状态（队列 1790~2044）。
- **操作**：恢复上行，静置到积压清空（≈68 分钟），期间继续采样。
- **预期**：
  - 每 3 条历史插 1 条最新（契约 §8.2），实时数据不被饿死；
  - 补传速率 ≈ 1 条/2s，清空后回到 1 条/10s；
  - 补传的 `msg_id` 若与断网前已发过的重复，云端去重命中（重复不报错）；
  - 清空后 `pending` 归零，`dropped` 不再增长。
- **判定**：补传速率明显低于 1 条/2s（比如卡在某个 `msg_id` 反复重发）→ 查退避/ACK 匹配；
  云端出现重复写入（不是去重而是新增）→ 云端去重逻辑要看。

### D. 迁移过程中断电

迁移窗口很窄（正常联网时毫秒级，断网积压时 1~2s），人为命中很难。两个做法：

1. **随机断电法**（推荐）：进入 B 状态后，每 30s 断一次电、5s 后上电，重复 **20 次**。
   20 次里必然有几次落在迁移或写入中间。
2. **定时断电法**：用一个可编程插座，按 43 分钟周期断电（对齐 42m30s 的迁移节奏），
   连续 10 个周期。

- **预期（每次上电后检查）**：
  - `boot_id` 严格 +1；
  - 云端仍能继续收到补传，`seq` 缺口仍只有 255 的整数倍；
  - 没有"卡住不动"（连续两次上电后 5 分钟内没有任何新 `msg_id` = 失败）；
  - 没有出现 `boot_id` 回到 1（S4/S7 被误擦）。
- **判定失败的含义**：断电后不再补传 = 扇区选择/提交标识有问题（迁移未完成时应回退旧扇区）；
  缺口不是 255 整数倍 = 迁移把未提交的数据算成了已完成。

## 5. Flash 兼容性（旧固件能不能读新记录）

本轮**没有改记录格式**。64B 记录布局、CRC 覆盖 `[0..53]`、提交标识 `[55]=0x00`、
确认字 `[60..63]` 全部与 `1d48590` 一致。

| 方向 | 结论 |
|---|---|
| 新固件读 1d48590 写的记录 | ✅ 正常。旧固件从不写 `[54]`，确认字保持 `FF` → 读为待发 |
| 1d48590 读新固件写的记录 | ✅ 正常。旧固件对确认字"非 0 即待发"，与本轮保守规则一致 |
| 32bd0a6 之前的固件读新记录 | ⚠️ 能读，但会把所有记录当待发全部重发一遍（旧格式的确认位在 `[54]`）。云端去重可吸收，不会脏数据 |

真正发生格式变化是 `32bd0a6`（确认位从 `[54]` 移到 `[60..63]`，提交标识独立）。
从 `1d48590` 到本轮**无格式变化**，所以可以在保留 S4~S7 的前提下互换固件。

## 6. 内存验收口径

不能拿芯片 192KB 当预算。按实际链接区域算：

| 区域 | 起始 | 链接上限 | 实际占用 |
|---|---|---|---|
| RW_IRAM1 | 0x20000000 | 0x1C000 = **112KB** | 0x9A88 = **39,560B (38.63KB)** |
| RW_IRAM2 | 0x2001C000 | 0x4000 = 16KB | 0（未使用） |
| CCM | 0x10000000 | 64KB | 未映射，不可用 |

- 可用预算 **112KB**，已用 38.63KB（34.5%），余量 73.4KB。
- 大头是 `s_queue`：2044 × 16B = **32,704B**（占 ZI 的 82.9%）；其余含 4KB 栈。
- 结论：要扩缓存只能动 `s_queue`，每加 100 条约 +1.6KB。
  按 112KB 预算，理论上限约 5500 条（还要留栈和 HAL 缓冲），但**不建议**：
  容量越大，断网积压后的单次迁移阻塞越久。

## 7. 擦写寿命估算（回答"长期稳定"）

每次迁移 = 2 次扇区擦除（擦目标 + 擦旧）。内部 Flash 标称 ≥10k 次。

| 场景 | 迁移周期 | 每天擦除次数 | 到 10k 次 |
|---|---|---|---|
| 60s 节律、正常联网 | 34h04m | ≈1.4 | **≈19 年** |
| 10s 节律（仅测试）、正常联网 | 5h40m | ≈8.5 | **≈3.2 年** |
| 10s 节律、长期断网（最坏） | 42m30s | ≈68 | **≈5 个月** |

两个结论：
1. **10s 测试节律不能留在现场**：按 10s 跑，扇区约 3 年就磨到 10k 次；
   验证完成后必须注释掉 `DTU_FAST_TEST_RHYTHM` 切回 60s。
2. 长期断网会显著加速磨耗 —— 这也是满缓存必须"丢最旧 1/8"而不是无限保留的原因。

## 8. 已知未验证 / 不在本轮范围

- 真实芯片掉电瞬间的编程行为（模拟器只能模拟"写一半"的形态，不能证明硅片行为）。
- `HAL_GetTick` 49.7 天回绕（代码用无符号差值比较，理论上可跨回绕，未跑等价时间压缩测试）。
- 位翻转（非掉电）造成的确认字异常：本轮的保守策略会把它当"待发"重传，
  不会漏传，但会多占一个槽。
- 看门狗、中断优先级、低功耗未涉及。
- 身份损坏仍需人工 `FS_IdentityRepair(云端已知最大编号)`，
  **不会**因为"数据区为空"就自动重新编号（数据区为空不能证明从未使用过）。
