# JY_EnvMon 上板测试计划（v3：无仪器版）

> 适用代码：`e8990a0` + 本轮"屏幕可观测 / 断电阶段自证 / 看门狗重算"修正（工作区）
> 节律：如无特别说明，均按 `DTU_FAST_TEST_RHYTHM` 打开计算（10s/条、2s 发送槽、每 3 条历史插 1 条最新）。
> **前提：现场没有示波器、不接 GPIO、不接调试串口。** 所有观测必须由设备自己给出，
> 落在 **LED 屏** 和 **云端** 两处。本轮为此新增了"迁移阶段自证"和"喂狗间隔"两个指标。
> 本文所有"预期"都写明判定口径；口径不成立的，宁可记为"未验证"，不写成"通过"。

## 1. 本轮代码变化（烧录前必须知道）

| 变化 | 内容 | 为什么 |
|---|---|---|
| **看门狗超时 4s → 8s（名义）** | `app.c`：`Prescaler=256`、`Reload=1000` | LSI 是 17/32/47kHz（min/typ/max），"4s 标称"实际可能是 2.72s；而 128KB 扇区擦除 max 2s，余量只剩 0.7s。改后最坏（47kHz）为 **5.45s**，对 2s 擦除仍有 2.7 倍余量；但 5.45s 只是计算值，**必须用 D5 实测复核** |
| 迁移按进展喂狗 | `FS_SetProgressHook()`：擦完一个扇区、每复制 32 条、写完完成标识各回调一次 | 整段迁移 1~2s 以上，只有一个超时值时靠"整段喂一次"不安全；按进展喂才是正确做法（Flash 真卡死则没有进展，仍会复位） |
| **喂狗间隔统计** | `AppDiag_t.max_feed_gap_ms`：`App_FeedWatchdog()` 里量相邻两次喂狗的间隔 | **这是"离狗复位还有多远"的唯一直接指标**，无需示波器。注意不能用 `max_loop_ms` 代替：迁移期间整圈可达 2s+ 但不复位 |
| **断电阶段自证** | `FS_Diag_t.last_int_phase`：`FS_Init` 时扫两个数据扇区反推上次迁移没走完的现场（`FS_InferInterrupted`） | 没有 GPIO 打点，就必须让 Flash 自己作证；但同一种残留可能对应多个时刻，判据见 §2.3 的"三态说明" |
| 屏显诊断页 | `Screen_ShowText()` + `app.c` 的 10 个诊断页（`APP_DIAG_PAGES`） | 现场唯一读数窗口；新增"采集/屏显"两页用于拆解喂狗间隔。量产值 0，诊断代码与字符串一起消失 |
| 强制迁移开关 | `APP_FORCED_MIG_TEST`（默认 0，D 组置 1） | 让"随机断电"能真的命中迁移窗口 |
| 复位原因 | `reset_cause`（读 `RCC->CSR` 后清标志） | 区分人为断电 / 看门狗 / 欠压；`IWDG` 一出现立即停测 |
| 固定分散加载 | `MDK-ARM/JY_EnvMon_limit64k.sct`（`umfTarg=0`） | Target 对话框的 IROM1 Size 已被 Keil 回写两次，保护会静默失效 |

**数据路径没有改动**：记录格式、CRC 覆盖范围、提交标识、确认字语义、迁移顺序全部与 `e8990a0` 相同。新增的是回调、计数、一次性耗时统计和只读的反推。

## 2. 先决条件

### 2.1 烧录必须保留 S4~S7

| 扇区 | 地址 | 内容 |
|---|---|---|
| S4 | 0x08010000–0x0801FFFF (64KB) | 元数据 A（boot_id/代次） |
| S5 | 0x08020000–0x0803FFFF (128KB) | 数据缓存 A |
| S6 | 0x08040000–0x0805FFFF (128KB) | 数据缓存 B |
| S7 | 0x08060000–0x0807FFFF (128KB) | 元数据 B |

Keil：`Options for Target` → `Debug` → `Settings` → `Flash Download`，**取消 `Erase Full Chip`，改选 `Erase Sectors`**。
ST-LINK Utility / CubeProgrammer：擦除范围填 `0x08000000`–`0x0800FFFF`，不要点 `Full chip erase`。
全片擦除 = boot_id 归零（下次从 1 重编，撞云端历史）+ 最多 2044 条缓存丢失，两者都不会报警。

烧完第一件事：看屏显"代次"页，**必须是上一次的值 +1 左右，不是 1**。

### 2.2 构建核对（每次构建后都看 map，不看对话框）

```
Load Region LR_IROM1 (Base: 0x08000000, Size: 0x00005d74, Max: 0x00010000, ABSOLUTE)
Execution Region RW_IRAM1 (Exec base: 0x20000000, Size: 0x00009c80, Max: 0x0001c000)
```

`Max` 不是 `0x00010000` 就说明固定 scatter 没生效，**停止烧录**。
本轮实测：`Code=22550 RO=1238 RW=136 ZI=39928`，ROM **23.4KB / 64KB**，`RW_IRAM1` **40,064B / 112KB（34.9%）**。
已验证：把 Target 对话框的 IROM1 Size 手动改回 `0x80000` 再编译，map 里 `Max` 仍是 `0x00010000`。

### 2.3 屏显诊断页：现场唯一的读数窗口

8 个正常页之后紧接 10 个诊断页（每页停 5s），**上电立刻停在第一个诊断页**，整轮 8+10 页约 2 分 30 秒。

| 顺序 | 屏上名称 | 读数含义 | 判据 |
|---|---|---|---|
| D0 | **阶段** | `OK` / `M2` / `M3`：**上次**迁移没走完时留下的现场（上电时由 Flash 反推，跨复位有效）。语义见下方"三态"说明，**不是**唯一断电时刻 | D 组核心指标，见 §5-D |
| D1 | 待发 | 未确认队列条数（`pending`） | A 组应长期个位数；B 组涨到 2044 后停在 1790 附近；C 组单调下降 |
| D2 | 丢弃 | 容量淘汰累计（`dropped`） | **正常联网时应恒为 0**；满缓存后每次恰好 +255 |
| D3 | 迁移 | 左=成功次数，`F`+右=失败次数 | `F0` 恒成立；出现 `F1` 以上要查 `阶段` 页 |
| D4 | 复位 | `POR`/`PIN`/`SOFT`/`BOR`/`IWDG`… | 人为断电后应为 `POR`；**出现 `IWDG` 立即停测** |
| D5 | 喂狗 | 相邻两次喂狗的最大间隔（ms） | ①**安全判据：必须 < 3000**；②理论极限 5450（47kHz LSI）；③实测值本身是数据，不预设"正常 1000~1300"，按实际擦除时间解释 |
| D6 | 耗时 | 单次迁移最长耗时（ms，含 2 次擦除） | 用于解释 D5：`D5 ≈ 单次擦除 + D8 + D9` |
| D7 | 代次 | 本次启动的 `boot_id` | 每次上电递增；**不允许回退/复用** |
| D8 | 采集 | 单次 `Sensor_Collect()` 最长耗时（ms） | 与 D9 一起拆解 D5；迁移不在此项内 |
| D9 | 屏显 | 单次刷屏最长耗时（ms） | 串行送屏，可能是 D5 里除擦除外的主要项 |

> **三态说明（本轮修正）**：`阶段` 页只能证明"上次迁移没走完"，**不能**唯一确定断在哪一步。
> - **确定**：`M2` = 目标扇区头已写、提交标识未写 → 中断发生在"复制开始之后、提交之前"这一段内。
>   这一段内部（复制第几条、写提交字的那一刻）**无法再区分**。
> - **可能**：`M3` = 两个扇区都已提交、旧扇区未擦完 → 可能死在"提交之后擦旧扇区之前/之中"，
>   也可能只是"迁移校验失败返回 −1"后没做收尾（两种情况 Flash 现场相同）。
> - **未知**：`OK` 既可能是真没中断，也可能是"死在擦目标扇区"（擦除不留痕迹），
>   还可能是校验失败；三者不可区分，**不得据此断言"没发生过中断"**。


### 2.4 云端（第二证据源）

`msg_id = JY001/<boot_id>/<seq>`。看：`seq` 连续性、节奏、重复去重命中、旧 `boot_id` 的历史补传。
云端与屏显不一致时，**以屏显为准**（云端只能看到"发出来了什么"，看不到"本地还有多少没发"）。

## 3. 时间/容量换算（10s 节律）

| 量 | 数值 |
|---|---|
| 单扇区容量 | 2044 条 |
| 填满一个扇区 | 2044 × 10s = **5h40m40s** |
| 满后每批淘汰 | 255 条（容量 1/8） |
| 每批间隔 | 255 × 10s = **42m30s**（≈1.41 次迁移/小时） |
| 第 2045 条后队列 | 2044 − 255 + 1 = **1790 条**（1789 是"丢完、未追加"的中间态） |
| 2044 条补传清空 | **理想下限 85.2 分钟**（0.4 条/s 净消化），实际更长，不作验收线 |

净消化推导：发送槽 2s/条 → 0.5 条/s；同期新增 0.1 条/s；稳态 ≈ 0.4 条/s。
串口发送、ACK 往返、退避重试、3:1 插队都会让它更低，所以**必须实测**（每 10 分钟记一次"待发"，算斜率）。

## 4. 看门狗：计算只用于选参数，验收必须实测

### 4.1 超时不是"8 秒"，是一个区间

`Reload=1000`、`PSC=256` 时，超时 = `(1000+1) × 256 ÷ f_LSI`：

| LSI | 超时 | 性质 |
|---|---|---|
| 17 kHz（min） | **15.06s** | 真卡死时最晚才复位 |
| 32 kHz（typ） | **8.00s** | **这就是"8s"的来历，只是名义值** |
| 47 kHz（max） | **5.45s** | **安全判定一律用这个值** |

> 若按 `Reload=2000、PSC=128` 也是同一结果：`2001×128÷47000 ≈ 5.45s`。
> 关键不是"8"，而是"最快 LSI 下还剩多少"，即 **5.45s**。

### 4.2 完整调用路径与喂狗点：两次擦除**不叠加**

迁移的完整路径是
`FS_Append` → 队列满 → `FS_RecycleFrom(drop)` → `FS_CopyPendingTo()` → 返回 → 擦旧扇区。

按当前代码逐个动作核对喂狗位置（`App/flash_store.c` 行号为本轮版本）：

| # | 动作 | 位置 | 喂狗 | 该动作本身耗时上界 |
|---|---|---|---|---|
| ① | 主循环末尾喂狗 | `app.c` `APP_Loop` | ✅ | —（进入迁移前最后一次） |
| ①a | **采集 / 刷屏 / 串口 / `FS_Append` 前处理** | ①到②之间 | ❌ | **无手册上界**，见 4.3 |
| ①b | **擦除前补喂**（本轮新增） | `FS_CopyPendingTo` 里 `FS_Phase(ERASE_TARGET)` 之后 | ✅ | — |
| ② | **擦目标扇区** | `FS_EraseSector(target)` | ✅ 已在①b补 | **≤2s**（HAL 轮询，不可切分） |
| ③ | 擦完目标扇区 | `FS_Progress()` | ✅ | — |
| ④ | 写扇区头 + 回读 | 4 个字 | — | <5ms |
| ⑤ | 复制循环，每 32 条 | `if (copied % FS_PROGRESS_STEP == 0) FS_Progress()` | ✅ | 32 条 × 16 字 × 100µs ≈ **51ms** |
| ⑥ | 复制尾部（不足 32 条） | 循环结束前 | ❌ 不单独喂 | ≤31 条 ≈ **50ms** |
| ⑦ | 写提交字 + 回读 | `FS_PHASE_COMMIT` 后 `FS_Progress()` | ✅ | <5ms |
| ⑦b | **擦旧扇区前补喂**（本轮新增） | `FS_RecycleFrom` 里 `FS_Phase(ERASE_OLD)` 之后 | ✅ | — |
| ⑧ | **擦旧扇区** | `FS_EraseSector(old)` | ✅ 已在⑦b补 | **≤2s** |
| ⑨ | 擦完旧扇区 | `FS_Progress()` | ✅ | — |

**关键结论**（本轮修正了上一版的错误）：

```
上一版：最长不喂狗 = 单次擦除 ≈2.1s
        错在只从②算起。真实路径是 ① → 采集/刷屏/串口/FS_Append 前处理 → ②，
        这一段没有任何手册上界，被漏在预算外。

本轮：在两处擦除前各补一次 FS_Progress()，于是
最长连续不喂狗 = max( 主循环体(采集+刷屏+串口+前处理) , 单次擦除≈2.0s + 前后编程 <10ms )
                = max( 不可测的循环体 , 2.01s )
```

- 补喂之后，**不可测的采集/刷屏不会再叠加到擦除上**；它们只影响"主循环体"这一段，
  而这一段长度 D5（`max_feed_gap_ms`）+ D8/D9 实测就能直接看出来。
- ③⑤⑦⑨ 把两次擦除**隔开**，不存在"2s + 2s = 4s"的叠加。
- ⑥ 的"尾部不喂狗"最多 50ms，落在 ⑤ 与 ⑦ 之间，不影响量级。
- 同一个 `FS_Append` 里**不会连续触发两次迁移**：`FS_RecycleFrom` 之后
  `s_used = keep = 1789`，小于单扇区容量 2044，不会紧接着再走一次 `FS_Recycle`。
  否则才是"4 次擦除串起来"，这一条要作为回归项保留。
- `FS_Init` 的首次擦除发生在 `Dtu_Init` 内、早于 `App_IwdgInit()`，
  **那时 IWDG 还没启动**，不受超时约束（这也是它可以不喂狗的原因）。

对照最坏超时 5.45s：

```
5.45s − 2.01s = 3.44s 余量（2.7 倍）—— 这一项现在是确定的
剩余不确定项只有"主循环体"本身，由 D5 实测给出上界
```

### 4.3 主循环体：采集 / 刷屏 / 串口

补喂之后它们**不在擦除那一段里**，但仍然是"①→①b"之间唯一的内容，
所以 `max_feed_gap_ms` 实际测到的就是这一段的长度（除非那段正好赶上迁移，则测到 2.01s）：

| 项 | 上界 | 依据 | 确定性 |
|---|---|---|---|
| 采集 | **未知** | 485/BLE 读超时未在手册中给定 | **必须实测（D8）** |
| 刷屏 | **未知** | 串行送屏，取决于字模与波特率 | **必须实测（D9）** |
| 串口发送 | 未知但小 | 单行 JSON，非阻塞投递 | 实测观察 |
| 其他 | — | 传感器调度、状态机 | 实测观察 |

要求：

```
max_feed_gap_ms（D5）< 3000
且 D8(采集) + D9(屏显) + 串口 < 5000（否则即使没有迁移也会被咬）
```

这 3.44s 余量**是推算出来的，不是实测余量**。如果实测 `max_feed_gap_ms` 逼近 3000，
说明采集或刷屏吃掉了预算，必须拆开看 D8/D9，而不是"再加大超时"了事
（加超时只会把"真卡死"的发现时间推得更晚）。

### 4.4 验收线（A 组必检，实测）

1. **`max_feed_gap_ms` < 3000**（相对 5.45s 保留 ≥ 2.45s，约 45% 余量）；
2. 同时抄 **D8 采集 / D9 屏显 / D6 迁移耗时**，用于解释 D5 的构成；
3. 至少覆盖一次"积压满触发迁移"的完整迁移（D6 有值），否则没测到最坏段；
4. **出现 `IWDG` 复位即判失败**，不再继续跑数据；
5. 实测 `max_feed_gap_ms` 才是结论；`max_loop_ms` 在迁移期间会超过超时属正常
   （那一圈是按进展喂的），**不要用 `max_loop_ms` 判断会不会被咬**；
6. 206 条主机测试通过、编译 0 错 0 警，只证明逻辑与链接，**不证明这块板子的时序**。

> 为什么要实测：擦除时间随批次/温度变化（typ 1s、max 2s，相差 100%），
> 刷屏时间取决于字模与显示控制器，采集时间取决于 485/BLE 超时。
> 这三项都没有"必然如此"的保证，计算只能保证"设计上留了余量"，不能保证"这一块板子一定不会咬"。


## 5. 四组上板测试

### A. 正常联网、ACK 正常（可立即开始）

- 前置：云端在线并回 `status=stored`；记下起始 `seq` 与"代次"。
- 操作：连续跑 **≥ 2 个扇区 = 4088 条 ≈ 11h20m**，中途重启 1 次（用复位按键，别断电）。
- 预期：
  - "待发"长期 0~3；"丢弃"**恒为 0**（这是"没丢数据"的最直接证据）；
  - "迁移"成功次数每小时 ≈1.4；**失败数恒为 0**；
  - "喂狗" **实测记录，判据 <3000**（不要预设"正常 1000~1300"，实际值取决于这块板子的擦除时间）；
  - "耗时" 与 D8/D9 一起解释喂狗间隔；
  - "复位"为 `PIN`/`SOFT`/`POR`，**无 `IWDG`**；
  - 重启后"代次"+1，`seq` 从 1 重开（历史补传仍用旧代次，云端可见两个 `boot_id` 交替）。

### B. 断网积压（不给 ACK）

- 前置：A 完成；断开上行（拔 DTU 或云端禁用）。
- 操作：保持采样 **≥ 7h**（5h40m 填满 + 至少 2 次 42m30s 迁移 ≈ 7h05m）。
- 预期：
  - 前 5h40m："待发"线性增长到 2044；
  - 第 2045 条："待发" → 1790，"丢弃" += 255，"迁移" +1；
  - 之后每 42m30s 一次，"丢弃"每次 +255。
- 判定：
  - **"丢弃"只在满缓存之后增长，且每次恰好 +255**（设备侧主判据）；
  - 云端缺口只作辅助，**不能要求缺口是 255 的整数倍**：被淘汰那批里可能有"其实已入库、只是 ACK 丢了"的记录，
    它们本来就不在缺口里。正确表述：**缺口 ≤ "丢弃"计数，且只出现在断网区间**；
  - "迁移"页出现 `F1` 以上 → 停测，看"阶段"页与"耗时"页。

### C. 恢复补传

- 前置：B 结束、仍处于积压状态（1790~2044）。
- 操作：恢复上行，继续采样，直到"待发"清零。
- 预期：
  - 每 3 条历史插 1 条最新，实时数据不被饿死；
  - "待发"单调下降（插队与重试会造成短时持平，属正常）；
  - "丢弃"不再增长；
  - 清空后回到 1 条/10s。
- 判据：**实测净消化速度**（每 10 分钟抄一次"待发"求斜率），不给固定分钟数。
  85.2 分钟是理想下限，两倍以上才叫异常。
- 补传期间若积压仍 >1790 又触发迁移，"待发"会先 −255 再继续降，属正常。

### D. 迁移中断（无仪器版）

**观测原理**：不需要知道断电的精确时刻。每次上电屏显"阶段"页就会告诉你：
上次那次迁移死在哪一步。判定依据是"断电后记录一条不少 + 阶段可解释"，而不是"断电时刻可复现"。

**准备**：
1. 先完成 B（有 1790~2044 条积压，迁移才有内容可复制）；
2. 把 `App/app.c` 的 `APP_FORCED_MIG_TEST` 改成 **1**，重新编译烧录（**测完必须改回 0**）；
3. 确认屏显"迁移"页计数在涨（每 15s +1），说明强制迁移生效。

**做法**：上电后**随机时刻**拔电，重复 **≥15 次**，每次重新上电记三项：阶段 / 待发 / 代次。

| 屏上"阶段" | 能确定什么 | 断电后应有的结果 |
|---|---|---|
| `M2` | **确定**：目标扇区头已写、提交标识未写，中断落在"复制开始之后、提交之前"这一段内（段内具体时刻无法再区分） | "待发" = N（不变）；目标扇区被丢弃；下次迁移重新擦它 |
| `M3` | **可能**：两扇区都已提交、旧扇区未擦完 → 可能死在"提交后、擦旧扇区前/中"；**也可能**只是迁移校验失败返回 −1（两种现场相同） | "待发" = N（新扇区已提交）；或 N−255（若那一次本来就该淘汰） |
| `OK` | **未知**：既可能没中断，也可能死在"擦目标扇区"（擦除不留痕），也可能是校验失败；三者不可区分 | "待发" = N；旧扇区完好 |

**通过条件**（不再要求"每个阶段各命中 5 次"，因为阶段现场无法唯一对应时刻）：
- 随机断电 **≥15 次**，其中至少 3 次在强制迁移生效期间（"迁移"计数在涨）断电；
- 每次"待发" ∈ {N, N−255}，**不出现第三种值**；
- 每次"代次" ≥ 上次值（不回退、不复用）；
- 每次"复位"为 `POR`；
- `M2`/`M3` 残留若出现，按上表核对"能确定什么/可能是什么"，**不据此断言唯一断电时刻**；
- 任意一次抽查：云端恢复后最旧的几条 `msg_id` 与设备侧一致（旧代次仍在补传）。

**不通过即停测的情形**：
- "待发"出现第三种值（丢记录，或把已确认记录复活）；
- "代次"回退到更小的值（身份被破坏 → 只能人工 `FS_IdentityRepair`）；
- "阶段"页出现 `M2`/`M3` 以外的非 `OK` 值；
- 上电后 30s 内"待发"不更新、"迁移"计数完全不涨（卡死）。

**说明**：阶段 1（擦目标扇区）断电**不留痕迹**，且那时旧扇区完好、数据一条没少，
所以它没有独立的判定需求；`OK` 里就包含这种情况，不必强求命中。

## 6. Flash 兼容性与回退（格式可读 ≠ 行为不等价）

记录格式本轮未变：64B、CRC 覆盖 `[0..53]`、提交标识 `[55]=0x00`、确认字 `[60..63]`。
所以"能读出来"成立，但**行为不等价**：

| 回退到 | 能读新记录 | 行为差异 |
|---|---|---|
| 本轮 / `7c6573a` / `e8990a0` | — | 基准（`e8990a0` 只是诊断差异，数据路径一致） |
| `1d48590` | 能 | 不认识"陈旧副本"关系（无 `FS_HasLaterCopy`）：换槽留下的旧副本会被当成第二条待发 → 重复上传 + 白占槽 |
| `3fa0bdd` | 能 | **禁止回退**：它把"非 FF 非 00"当已确认，会把本轮"状态不确定"的记录直接当成功出队 → 漏传 |
| `32bd0a6` 之前 | 能 | 确认位在 `[54]`，会把所有记录当待发重发一遍（云端去重吸收） |

结论：**向前升级可以直接做；回退不是"换个 hex"，需要专项验证去重/队列恢复/确认策略。**

## 7. 内存验收（按实际链接区域，不用 192KB）

| 区域 | 起始 | 链接上限 | 本轮实测 |
|---|---|---|---|
| RW_IRAM1 | 0x20000000 | 0x1C000 = 112KB (114,688B) | 0x9C80 = **40,064B (34.9%)** |
| RW_IRAM2 | 0x2001C000 | 0x4000 = 16KB | 0（未使用） |
| CCM | 0x10000000 | 64KB | 未映射，不可用 |

- `s_queue` = 2044 × 16B = 32,704B，占 ZI 的 **81.6%**；其余含 4KB 栈、屏幕帧缓冲、诊断页字符串。
- 扩容量只能动 `s_queue`：每 +100 条约 +1.6KB；但容量越大，积压后单次迁移阻塞越久（§4）。

## 8. 擦写寿命（每扇区口径）

每次迁移擦 **2 个**扇区（目标 + 旧），**两个扇区各承担 1 次擦除**。按每扇区 10,000 次预算：

| 场景 | 迁移周期 | 每扇区到 1e4 次 |
|---|---|---|
| 60s 节律、正常联网 | 2044 × 60s = 34h04m | ≈ **38.9 年** |
| 10s 节律（仅测试）、正常联网 | 5h40m | ≈ **6.5 年** |
| 10s 节律、长期断网（最坏） | 42m30s | ≈ **9.7 个月** |
| **D 组强制迁移 15s 一次（仅测试）** | 15s | ≈ **1.7 天** |

四个前提：
1. 这是**擦除次数预算**，不是寿命保证；要看所用型号的 program/erase cycles、温度与数据保持条件。
2. 10s 节律只是测试用，验证完必须注释掉 `DTU_FAST_TEST_RHYTHM`（切回 60s/5s）。
3. **`APP_FORCED_MIG_TEST` 只能用几小时**（15s 一次会快速消耗擦写预算），测完立即改回 0。
4. 长期断网是最坏场景 —— 这正是满缓存"丢最旧 1/8"而不是无限保留的理由。
   元数据扇区另有磨损：每开机追加一条编号记录，S4 可存 2040 条 → 2040 次开机才擦一次，可忽略。

## 9. 串口旁路（本版不需要，留作以后有条件时）

USART1 是 9600 8N1，**MCU 侧 3.3V TTL（PA9=TX / PA10=RX），DR154 侧才是 RS232 电平**。

- 监听设备发出：USB-TTL 的 **RX → PA9**，GND 共地。
- 监听 DR154 回复：USB-TTL 的 **RX → PA10**。
- **一路 RX 不能同时看两个方向**；要同时看需两路 USB-TTL 或双通道逻辑分析仪。
- **禁止**把 USB-TTL 直接接 DB9（RS232 ±12V 会打穿 TTL 侧），必须经 MAX3232 之类电平转换。
- 只做"听"：TX 悬空不接。

## 10. 已知未验证（不要据此下"长期稳定"结论）

- **真实芯片的掉电瞬间编程行为**：主机侧是严格 F4 模拟 + 故障注入，能证明代码逻辑，不能证明硅片时序。
- **`max_feed_gap_ms` 的真机数值**：本轮只有计算区间（5.45s~15.06s 超时、擦除 ≤2s），<3000 是验收线；
  A 组就是去取这个数，取不到就不能说"看门狗没问题"。
- **擦除/屏显/采集的真实耗时**：分别由 D6/D9/D8 读取；三者相加应能解释 D5，解释不了说明还有未计入的阻塞段。
- **`HAL_GetTick` 49.7 天回绕**：代码用无符号差值，理论上可跨，未做等价压缩测试。
- **位翻转（非掉电）**造成的确认字异常：按"待发"处理，不会漏传，但会多占槽。
- **中断优先级与低功耗**未涉及；`HAL_UART_ErrorCallback` 的 ORE 恢复只在代码层验证过。
- **身份损坏仍需人工** `FS_IdentityRepair(云端已知最大编号)`，不会因"数据区为空"自动重新编号。
- 屏显诊断页的"阶段"只在**本次上电扫描时**确定一次；运行中再发生迁移失败，只反映在"迁移 F 计数"上。
