## 0. v2 相对上一版修正了什么

| 编号 | 上一版（错） | 本版（修正） |
|---|---|---|
| 1 | "无看门狗，不会复位" | **IWDG 已启用（4s 标称）**，只在主循环末尾喂；迁移期间会被复位。本轮已改为"按进展喂狗"，但仍必须实测迁移耗时与复位原因 |
| 2 | "补传清空 ≈ 68 分钟" | 68 分钟只是 2044×2s，忽略同期新增。**理想下限 = 2044 / (0.5−0.1) ≈ 85.2 分钟**，实际更长；只作为参考值，不作验收线，以实测净消化速度为判据 |
| 3 | "每 30s 断电 20 次，必然命中断电" | 迁移周期 42m30s，30s 周期几乎撞不上。改为**按阶段定点断电**（需阶段标记），随机断电只作补充 |
| 4 | "boot_id 严格 +1"、"缺口必须是 255 整数倍" | 改为：**新记录用的代次不回退、不复用**；缺口允许因"已入库但 ACK 丢失"而非 255 整数倍，判据改为"缺口 ≤ dropped 计数且只出现在断网区间" |
| 5 | "新旧固件可直接互换" | 改为：**格式可读 ≠ 行为等价**；回退后的去重/队列恢复/确认策略需专项验证 |
| 6 | 寿命表把两次擦除算在一个扇区头上（19 年/3.2 年/5 个月） | 按**每扇区每次迁移各擦 1 次**重算：**38.9 年 / 6.5 年 / 9.7 个月**；且这是擦除次数预算，不是寿命保证 |
| 7 | "USB-TTL 并联在 USART1 上"（含糊） | 明确：只能接 **MCU 侧 TTL 电平**，单路 RX 只能看一个方向，禁止直连 RS232 |

## 1. 本轮代码变化（烧录前必须知道）

| 变化 | 内容 | 为什么 |
|---|---|---|
| 迁移按进展喂狗 | `FS_SetProgressHook()`：擦完一个扇区、每复制 32 条、写完完成标识各回调一次；`app.c` 里挂成 `HAL_IWDG_Refresh` | 迁移耗时是"秒级"，而 IWDG 标称只有 4s。原来是"复位→满缓存→立刻又迁移→又复位"的死循环风险 |
| 迁移可观测 | `FS_SetPhaseHook()`（阶段 1 擦目标 / 2 复制 / 3 提交 / 4 擦旧 / 0 空闲）、`FS_GetDiag()`（次数、失败次数、last_ms、max_ms、失败阶段） | 定点断电必须有"当前在哪个阶段"的坐标；阻塞时长必须实测 |
| 复位原因 | `APP_GetDiag()` 里的 `reset_cause`（上电时读 `RCC->CSR` 后清标志） | 区分"人为断电 / 看门狗 / 欠压"，否则无法判断是否被狗复位 |
| 整圈耗时 | `APP_GetDiag()` 里 `max_loop_ms`（主循环单次迭代最长耗时，含采集+屏显+迁移）、`max_collect_ms`、`max_screen_ms` | 需求就是把"采集、串口发送、迁移"合并测量；单独量某一项没有意义 |
| 固定分散加载 | `MDK-ARM/JY_EnvMon_limit64k.sct`，工程改为使用该文件（`umfTarg=0`） | Target 对话框里的 IROM1 Size 已被 Keil 回写成 `0x80000` 两次，保护会静默失效。改用固定 scatter 后，即使 IROM 显示 0x80000，链接仍受 64KB 限制 |

**数据路径没有改动**：记录格式、CRC 覆盖范围、提交标识、确认字语义、迁移顺序全部与 `7c6573a` 相同。新增的只有回调、计数和一次性耗时统计。

## 2. 先决条件

### 2.1 烧录必须保留 S4~S7

| 扇区 | 地址 | 内容 |
|---|---|---|
| S4 | 0x08010000–0x0801FFFF (64KB) | 元数据 A（boot_id/代次） |
| S5 | 0x08020000–0x0803FFFF (128KB) | 数据缓存 A |
| S6 | 0x08040000–0x0805FFFF (128KB) | 数据缓存 B |
| S7 | 0x08060000–0x0807FFFF (128KB) | 元数据 B |

Keil：`Options for Target` → `Debug` → `Settings` → `Flash Download`，**取消 `Erase Full Chip`，改选 `Erase Sectors`**。
ST-LINK Utility / CubeProgrammer：擦除范围填 `0x08000000`–`0x0800FFFF`，不要点 `Full chip erase`。
全片擦除 = boot_id 归零（下次从 1 重编，撞云端历史）+ 最多 2044 条缓存丢失，两者都不会报警。

### 2.2 构建核对（每次构建后都看，不靠记忆）

```
map 文件：Load Region LR_IROM1 (Base: 0x08000000, ..., Max: 0x00010000, ABSOLUTE)
```
`Max` 不是 `0x00010000` 就说明固定 scatter 没生效，**停止烧录**。
本轮实测：`Code=21666 RO=1202 RW=136 ZI=39504`，ROM 22.46KB / 64KB。

> 已验证：把 Target 对话框的 IROM1 Size 手动改成 `0x80000` 再编译，map 里 `Max` 仍是 `0x00010000` —— 固定 scatter 生效后，IDE 里的数值不再影响链接。

### 2.3 诊断怎么读（设备本身不显示队列状态）

三条通道，按可用性从高到低：

1. **云端**（主）：`msg_id = JY001/<boot_id>/<seq>`，看连续性、节奏、重复去重命中。
2. **调试器 live watch**（读内部状态）：Keil 进入调试后，Watch 窗口加
   `s_diag`（app.c 内：`reset_cause` / `max_loop_ms` / `max_collect_ms` / `max_screen_ms` / `loop_count`）
   与 `s_migdiag`（flash_store.c 内：`migrate_ok` / `migrate_fail` / `last_ms` / `max_ms` / `phase` / `fail_phase`）。
   需要勾选 `View → Periodic Window Update`。**不能用于断电测试**（复位即丢）。
3. **串口旁路**（可选，见 §9）：只能看线上帧，看不到内部计数。

## 3. 时间/容量换算（10s 节律）

| 量 | 数值 |
|---|---|
| 单扇区容量 | 2044 条 |
| 填满一个扇区 | 2044 × 10s = **5h40m40s** |
| 满后每批淘汰 | 255 条（容量 1/8） |
| 每批间隔 | 255 × 10s = **42m30s**（≈1.41 次迁移/小时） |
| 第 2045 条后队列 | 2044 − 255 + 1 = **1790 条**（1789 是"丢完、未追加"的中间态） |
| 2044 条补传清空 | **理想下限 85.2 分钟**（0.4 条/s 净消化），实际更长，不作验收线 |

净消化速度推导（用于 C 组判据）：发送槽 2s/条 → 0.5 条/s；同期新增 0.1 条/s；稳态下历史消化 ≈ 0.4 条/s。
但串口发送、ACK 往返、退避重试、3:1 插队都会让它低于 0.4 条/s，所以**必须实测**：
每 10 分钟记一次 `pending`，用相邻两点算实际斜率，斜率持续为负即正常，卡在某个值不变即失败。

## 4. 看门狗与阻塞预算（本版新增，最容易被忽略）

- IWDG：`Prescaler=128`、`Reload=1000`，LSI 标称 32kHz/128=250Hz → **标称 4.0s**。
- LSI 不是晶体，超时随温度/批次偏移；**4s 是标称值，实测可能明显更短**。
  **必须实测一次**：临时注释掉 `App_FeedWatchdog()` 的调用（或让主循环停住），
  用示波器量 USART1 TX 上"最后一帧结束 → 复位后第一帧"的间隔，记下来作为真实超时。
  这个数字决定后面所有"会不会被狗咬"的判断。
- 迁移耗时量级（估，需 `max_ms` 实测替代）：2 次 128KB 扇区擦除（各约 1s 量级）
  + 最多 32,704 个 word 编程（每个几十 µs 量级）+ 逐条回读校验 → **3~7s 量级**。
  也就是说：**不做按进展喂狗，满缓存迁移基本必然被复位**；而复位后队列仍满，
  10s 后下一次采样又触发迁移 —— 这就是本轮修掉的死循环。
- 合并测量口径：`max_loop_ms` 才是"离狗复位还有多远"，因为它把
  `Sensor_Collect`（485 收发）+ `Screen_ShowItem`（9600bps 阻塞发送）
  + `Dtu_Tick` 里的发送/重试 + 迁移全部包含在内。
- A 组必检：`max_loop_ms` < 实测看门狗超时的 **50%**。若接近，先看 `max_ms` 与 `max_collect_ms` 谁占大头。

## 5. 四组上板测试

### A. 正常联网、ACK 正常（可立即开始）

- 前置：云端在线并回 `status=stored`；记录起始 `seq`；清空或记下当前积压。
- 操作：连续跑 **≥ 2 个扇区 = 4088 条 ≈ 11h20m**，中途重启 1 次。
- 预期（每条都要能落到证据）：
  - 云端 `seq` 连续，无缺口（`dropped` 不增长的同义表述）；
  - 每 5h40m 一次迁移，迁移瞬间最多晚 1 帧（10s），不丢；
  - `migrate_ok` 每小时 ≈1.4 次递增，`migrate_fail = 0`；
  - `max_ms` / `last_ms` 记录在案（这是 §4 预算的实测值）；
  - `max_loop_ms` < 看门狗超时 50%；
  - 重启后 `reset_cause` 应为 `PIN`（编程器复位）或 `POWER_ON`；**出现 `IWDG` 立即停测**；
  - 重启后新记录使用新 `boot_id`，`seq` 从 1 重新开始（历史补传仍用旧 `boot_id`）。
- 记录表（每 30 分钟一行，或每次迁移一行）：

| 时间 | pending | dropped | migrate_ok | last_ms | max_ms | reset_cause |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

### B. 断网积压（不给 ACK）

- 前置：A 完成；断开上行（拔 DTU 或云端禁用）。
- 操作：保持采样 **≥ 7h**（5h40m 填满 + 至少 2 次 42m30s 迁移 ≈ 7h05m）。
- 预期：
  - 前 5h40m：`pending` 线性增长至 2044；
  - 第 2045 条：`pending` → 1790，`dropped` += 255，`migrate_ok` +1；
  - 之后每 42m30s 一次，`dropped` 每次 +255；
  - 全程不死机、屏幕继续刷新（`loop_count` 一直增长）。
- 判定：
  - **`dropped` 只在"满缓存"之后增长，且每次恰好 +255** —— 这是主判据（设备侧）；
  - 云端缺口只作辅助：恢复后最早收到的 `seq` 应对应"最后一次淘汰的边界"，
    但**不能要求缺口是 255 的整数倍**：被淘汰的那批里可能有"其实已入库、只是 ACK 丢了"的记录，
    它们本来就不在云端缺口里。正确表述是：**缺口 ≤ `dropped` 计数，且缺口只出现在断网区间**。
  - 若 `dropped` 每次不是 255、或迁移期间 `migrate_fail` 增长 → 停止，回查 `fail_phase`。

### C. 恢复补传

- 前置：B 结束、仍处于积压状态（1790~2044）。
- 操作：恢复上行，继续采样，直到积压清零。
- 预期：
  - 每 3 条历史插 1 条最新，实时数据不被饿死；
  - `pending` 单调下降（允许平台：插队与重试会造成短时持平）；
  - 同一条记录连续重发 ≥5 次 → 判失败（查 ACK 匹配/退避）；
  - 清空后回到 1 条/10s，`dropped` 不再增长。
- 判据：**实测净消化速度**（每 10 分钟采样 `pending` 求斜率），不给固定分钟数。
  85.2 分钟是理想下限，只用来判断"是否明显异常"（例如两倍以上才叫异常）。
- 补传期间若又触发迁移（积压仍在 1790 以上），`pending` 可能先 −255 再继续下降，属正常。

### D. 迁移过程中定点断电（需阶段标记）

迁移窗口在正常联网时只有毫秒级，积压时 1~7s，**30s 周期随机断电命中率极低**。做法：

1. **接阶段标记**（必须）：`app.c` 里注册阶段回调，一根空闲 GPIO 接示波器/逻辑分析仪：

```c
static void App_PhasePin(uint8_t ph)
{
    /* 高电平 = 正在迁移；阶段切换时拉低 20µs 做标记（4 段先后的时间轴即 1..4 阶段） */
    HAL_GPIO_WritePin(GPIOx, GPIO_PIN_y, (ph != FS_PHASE_IDLE) ? GPIO_PIN_SET : GPIO_PIN_RESET);
}
/* APP_Init 末尾：FS_SetPhaseHook(App_PhasePin); */
```
   引脚必须**先与 IO 分配表核对为空闲**（YC-24IO 上哪些脚可用我这边没有权威表，不猜）。
   若确实没有空闲脚：退而用调试串口打点（需 PA2/PA3 或其它空闲 UART）；两者都没有时，
   D 组只能记"随机断电覆盖，未定点"，**不能写成已验证**。

2. **断电点**：4 个阶段各 ≥5 次，共 ≥20 次，用示波器触发在目标阶段内手动/继电器断电。

| 阶段 | 断电后重新上电的预期 |
|---|---|
| 1 擦目标扇区 | 旧扇区完好，`pending` = 迁移前的 N，记录内容完整 |
| 2 复制记录（任意时刻） | 同上：N（目标扇区无完成标识 → 整个扇区被忽略） |
| 3 写完成标识（0xFFFFFFFF→0 那一瞬间） | N 或 N−255 二选一，不能是别的值 |
| 4 擦旧扇区 | N−255（新扇区已提交，旧扇区正在/已被擦） |

3. 判据（每次上电后）：
   - 启动正常、`loop_count` 增长，2 个采样周期内仍在发记录（不"卡死"）；
   - `pending` ∈ {N, N−255}，且抽查最旧/最新两条能读出且 CRC 通过；
   - `migrate_fail` 不因断电而误增（断电不走失败分支，复位后重新开始）；
   - **`boot_id` 判据改为**：新记录使用的代次**不回退、不复用**；
     不要求"每次上电 +1"（编号已持久化但还没上报就再次断电，云端看到跳号是允许的）。
     若观察到新记录 `boot_id` 小于该设备历史最大值 → 判失败（身份被破坏）；
   - 云端：允许缺口，允许旧 `boot_id` 的消息在补传期间穿插出现（历史记录保留原代次）。

4. 随机断电（每 30s 断一次，20 次）只作为补充，覆盖"阶段内的任意瞬间"，不替代上面的定点表。

## 6. Flash 兼容性与回退（格式可读 ≠ 行为等价）

记录格式本轮未变：64B、CRC 覆盖 `[0..53]`、提交标识 `[55]=0x00`、确认字 `[60..63]`。
所以"能读出来"是成立的，但**行为不等价**：

| 回退到 | 能不能读新记录 | 行为差异 |
|---|---|---|
| `7c6573a` / 本轮 | — | 基准 |
| `1d48590` | 能 | 不认识"陈旧副本"关系（无 `FS_HasLaterCopy`）：换槽留下的旧副本会被当成第二条待发 → 重复上传 + 白占槽；确认字"非 00 即待发"，与本轮保守策略一致 |
| `3fa0bdd` | 能 | **禁止回退**：它把"非 FF 非 00"当已确认，会把本轮"状态不确定"的记录直接当成功出队 → 漏传 |
| `32bd0a6` 之前 | 能 | 确认位在 `[54]`，会把所有记录当待发重发一遍（云端去重吸收） |

结论：**向前升级可以直接做；回退不是"换个 hex"那么简单**，需要专项验证（去重、队列恢复、确认策略），
在完成验证之前，不得对现场设备承诺"新旧固件可直接互换"。

## 7. 内存验收（按实际链接区域，不用 192KB）

| 区域 | 起始 | 链接上限 | 本轮实测 |
|---|---|---|---|
| RW_IRAM1 | 0x20000000 | 0x1C000 = 112KB (114,688B) | 0x9AD8 = **39,640B (34.6%)** |
| RW_IRAM2 | 0x2001C000 | 0x4000 = 16KB | 0（未使用） |
| CCM | 0x10000000 | 64KB | 未映射，不可用 |

- `s_queue` = 2044 × 16B = 32,704B，占 ZI 的 **82.5%**；其余含 4KB 栈。
- 扩容量只能动 `s_queue`：每 +100 条约 +1.6KB；但容量越大，积压后单次迁移阻塞越久（§4）。

## 8. 擦写寿命（按每扇区口径重算）

每次迁移擦 **2 个**扇区（目标 + 旧），因此**两个扇区各承担 1 次擦除**，不能把 2 次算到同一个扇区头上。
按每扇区 10,000 次擦除预算：

| 场景 | 迁移周期 | 每扇区到 1e4 次 |
|---|---|---|
| 60s 节律、正常联网 | 2044 × 60s = 34h04m | ≈ **38.9 年** |
| 10s 节律（仅测试）、正常联网 | 5h40m | ≈ **6.5 年** |
| 10s 节律、长期断网（最坏） | 42m30s | ≈ **9.7 个月** |

三个前提必须写清：
1. 这是**擦除次数预算**，不是寿命保证；具体要看所用型号的 program/erase cycles 指标、
   工作温度和数据保持（retention）条件。
2. 10s 节律只是测试用，验证完必须注释掉 `DTU_FAST_TEST_RHYTHM`（切回 60s/5s）。
3. 长期断网是最坏场景 —— 这正是满缓存"丢最旧 1/8"而不是无限保留的理由。
   元数据扇区另有磨损：每开机追加一条编号记录，S4 可存 2040 条 → 2040 次开机才擦一次，可忽略。

## 9. 串口旁路的正确接法

USART1 是 9600 8N1，**MCU 侧是 3.3V TTL（PA9=TX / PA10=RX），DR154 侧才是 RS232 电平**。

- 监听"设备发了什么"：USB-TTL 的 **RX → PA9**，GND 共地；设备 TX 是单向的，不会冲突。
- 监听"DR154 回了什么"：USB-TTL 的 **RX → PA10**。
- **一路 RX 不能同时看两个方向**。要同时看，需要两路 USB-TTL，或一个双通道逻辑分析仪
  （逻辑分析仪直接夹 PA9/PA10，3.3V 电平，最省事）。
- **禁止**把 USB-TTL 直接接到 DB9/RS232 的 TXD/RXD：±12V 会打穿 TTL 侧。必须经 RS232 电平转换（如 MAX3232）。
- 只做"听"：TX 悬空不接，避免两头发送打架。

## 10. 已知未验证（不要据此下"长期稳定"结论）

- **看门狗真实超时未实测**（LSI 容差），迁移 `max_ms` 未在真机测过 —— A 组的主要目的之一。
- 真实芯片掉电瞬间的编程行为：主机模拟只能造"写一半"的形态，不能证明硅片行为。
- `HAL_GetTick` 49.7 天回绕（代码用无符号差值，理论上可跨，未做等价压缩测试）。
- 位翻转（非掉电）造成的确认字异常：本轮策略按"待发"处理，不会漏传，但会多占槽。
- 中断优先级与低功耗未涉及；`HAL_UART_ErrorCallback` 的 ORE 恢复只在代码层验证过。
- 身份损坏仍需人工 `FS_IdentityRepair(云端已知最大编号)`，不会因"数据区为空"自动重新编号。
